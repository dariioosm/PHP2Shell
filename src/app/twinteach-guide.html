Twinteach:
¿qué hay que comprobar?

Procedimiento propuesto para sus administradores. No tenemos acceso a sus servidores ni conocemos sus versiones: no se afirma que esté protegido o comprometido.

NAVEGADORAngular

Envía peticiones a la API. No ejecuta el motor PHP.

→
BACKENDPHP + Laravel

El runtime PHP y su configuración son el foco de este caso.

→
RECURSOSBD / archivos

Los permisos y secretos accesibles al backend delimitan el impacto.

Esquema conceptual basado en el stack del enunciado; no representa una infraestructura verificada.

  1. Localizar todas las instalaciones

    Inventariar producción, pruebas, réplicas, contenedores y productos con PHP integrado. Anotar versión completa, proveedor del paquete, SAPI, extensiones y exposición a Internet. No basta con revisar el ordenador del desarrollador.

  2. Medir el PHP que realmente sirve Laravel

    Consultar la CLI y, por separado, el runtime del servidor mediante el panel del proveedor o un diagnóstico temporal restringido a administradores. En ese diagnóstico registrar PHP_VERSION, PHP_SAPI, php_ini_loaded_file() y valores efectivos de las directivas relevantes. Retirarlo al terminar; no publicar una página phpinfo().

    php -v
php --ini
php artisan about

    Ejecutar en el servidor o dentro del contenedor real. Estos comandos muestran el contexto CLI; no prueban por sí solos qué binario usa Apache o FPM.

  3. Contrastar parches y compatibilidad

    Comparar cada rama con la matriz de correcciones del sitio. Si la distribución aplica backports, exigir su aviso y la revisión del paquete. Revisar los requisitos de la versión de Laravel instalada antes de cambiar de rama PHP.

    Consultar mínimos upstream ↑

  4. Actualizar y renovar los procesos

    Probar primero en un entorno de pruebas y actualizar PHP con el paquete del proveedor o una imagen corregida. Reiniciar Apache/FPM o recrear contenedores; renovar servicios persistentes como Octane y colas cuando corresponda. Volver a medir cada instancia después.

  5. Revisar configuración y capas complementarias

    Aplicar el seguimiento de sesiones y comprobar la revisión Windows/Brotli si procede. Mantener APP_DEBUG=false en producción y servir Laravel desde public/. CORS, autenticación de Laravel o actualizar Angular no corrigen un fallo del intérprete.

    composer audit
composer check-platform-reqs
npm audit

    Son controles complementarios de dependencias y requisitos. Un resultado sin avisos no acredita que el runtime esté parcheado.

  6. Validar y conservar evidencias

    Probar login, sesiones, API, subida de archivos, colas e integración Angular–Laravel. Revisar registros y dejar constancia de versión efectiva web, revisión del paquete o imagen, fecha, reinicio y resultado de pruebas. Un escaneo de versión no sustituye esta comprobación.

CRITERIO DE CIERRE

Para estas dos CVE, todas las instancias deben ejecutar el parche upstream o un backport documentado, con procesos renovados y pruebas satisfactorias. El aviso posterior de sesiones se evalúa aparte. Esto acredita la corrección revisada; no descarta una intrusión anterior.

Base operativa: NCSC · NCSC-NL · Laravel, despliegue. El procedimiento es una adaptación al stack del enunciado.
